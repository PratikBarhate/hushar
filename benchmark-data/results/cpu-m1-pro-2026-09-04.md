# CPU benchmark — does pinning the batch axis pay off?

**Date** 2026-09-04 · **Host** MacBook Pro, Apple M1 Pro (8 performance + 2 efficiency cores),
32 GB · **Engine** ONNX Runtime 1.29.0, `cpu` provider, `intra_op_threads: 1`

Two questions.

**Does pinning the model's row axis improve CPU latency?** **No.** Unloaded, a model
compiled for exactly one row and a model with a dynamic axis are within 0.05 ms of each
other. Pinning earns its keep on a provider that *partitions* a graph, and the CPU
provider does not.

**What is the actual ceiling?** **At or above 500 req/s.** Both models held 500 req/s with
**zero shedding**, which the [2026-09-03 run](cpu-m1-pro-2026-09-03.md) did not — it shed
121 requests at 400 and 287 at 500. The difference is host load, not the service; see the
caveat at the end.

---

## What was measured

The same two models as the previous run, regenerated from the same script and seed —
49,353,733 and 50,101,253 parameters, `bench_model.onnx` at 188.3 MB and
`bench_named_model.onnx` at 191.2 MB.

`--with-batch1` writes a second copy of each, compiled with the row axis pinned to 1 and
paired with a configuration declaring `"fixed_batch_size": 1`. Both come from **one
variable in one loop iteration**, so the graph and the configuration cannot disagree about
the number:

```python
for suffix, rows in batches:                                    # rows is None or 1
    export(model, torch.randn(rows or 2, width), path, ["features"], rows=rows)
    config = vectorized_config(rng, f"{OUT_REL}/{name}.onnx", "cpu", rows=rows)
```

Checked rather than assumed, against all four artifacts on disk:

| configuration | `fixed_batch_size` | graph leading dim | agree |
|---|---|---|---|
| `bench_model_config.json` | absent | `rows` | yes |
| `bench_model_batch1_config.json` | 1 | 1 | yes |
| `bench_named_model_config.json` | absent | `rows` | yes |
| `bench_named_model_batch1_config.json` | 1 | 1 | yes |

**Load shape.** 1 row per request, 64 requests in flight maximum,
`connection_concurrency: 100`, 15 s measured per rate after warmup. Offered load is
open-loop: a request that finds no free slot is **shed and counted**, never allowed to slow
the generator down.

**No shedding anywhere, and `achieved` tracks `offered` to within 0.3 req/s.** So the
capacity ceiling was not reached at 500. p50 rises from ~11 ms to ~19 ms across the sweep,
which is queueing beginning rather than the engine slowing down: one inference costs ~11 ms
on one core, and eight performance cores at that rate is ~730 req/s in theory.

**The two feature paths cost about the same, with the named one consistently ahead.**
0.5 ms at 50 req/s and 2 ms at 500, in the named model's favour at every rate. That is the
question this model pair exists to answer, and the answer is that building twelve smaller
inputs is no more expensive than building one 502-wide vector — if anything slightly less.

**Feature handling is not where the time goes**, from the server's own metrics:

```
vectorized  metrics: 500 batches | mean us: VectorizationTime 12, ToTensorTime 0, InferenceTime 15809
named       metrics: 500 batches | mean us: VectorizationTime  8, ToTensorTime 0, InferenceTime 15642
```

Vectorizing 22 features takes 12 µs and wrapping the buffers takes under a microsecond,
against ~15.8 ms in the engine. The service accounts for about **0.07%** of a request, so
only a faster model moves this number.

## Results: pinned vs dynamic row axis

A pinned axis lets an engine specialise for one shape instead of generating code valid for
any size, so it is reasonable to expect it to be faster. On this provider it is not.

Unloaded, where the measurement is cleanest:

| model | dynamic axis | pinned to 1 | difference |
|---|---|---|---|
| vectorized @ 50 req/s | 10.82 ms | 10.85 ms | +0.03 ms |
| named @ 50 req/s | 10.78 ms | 10.75 ms | −0.03 ms |

Both differences are far inside run-to-run variance. **Pinning the row axis buys nothing on
the CPU provider**. What the field is actually for is serving a model that
was *already* exported with a pinned dimension: without `"fixed_batch_size"` such a model is
refused when it loads, because it could only ever be given batches of that one size.

### The measurement that looked like a difference, and was not

The first pass showed vectorized at 500 req/s as dynamic 54.19 ms / 31 shed against pinned
21.09 ms / 0 shed, which reads like a large win for pinning. It does not replicate. Running
the pair again with the **order reversed** inverted the result:

| | first pass | replicate (reversed order) |
|---|---|---|
| vectorized, dynamic | 54.19 ms, 31 shed | 19.24 ms, 0 shed |
| vectorized, pinned | 21.09 ms, 0 shed | 22.10 ms, 0 shed |

Three independent measurements of the *same dynamic configuration* at 500 req/s came out
**19.26, 54.19 and 19.24 ms**. The 54 is the outlier, and it was measured in the pass that
loaded four 190 MB models in one session. Two measurements of the pinned configuration came
out 21.09 and 22.10 ms.

The reading: at 500 req/s this host is close enough to saturation that a single measurement
is not evidence. That is worth stating as loudly as the result, because the first pass would
have supported the opposite conclusion.

---

## Caveats

**The rate sweep was run in one order only.** The 2026-09-03 run alternated the two models
to separate host-load drift from model differences; this one did not, so the
vectorized-vs-named gap above is weaker evidence than that run's. The pinned-vs-dynamic
comparison *was* replicated in both orders, which is why it is stated as a conclusion.

**Comparison with 2026-09-03 is across days, not controlled.** That run shed at 400 and 500
and reported p50 126 ms at 500; this one shed nothing and reported 19.26 ms. Same host, same
models, same engine, same configuration — the difference is what else the laptop was doing.
Neither run is wrong; the earlier one measured a busier machine. What survives both is the
part that does not depend on load: ~11 ms per inference on one core, the two feature paths
costing the same, and the service being a rounding error.

**500 req/s is a floor on the ceiling, not the ceiling.** Nothing shed, so the sweep never
found the knee. Finding it needs rates above 500.

## Reproducing

```bash
pip install -r scripts/requirements.txt
python scripts/generate_benchmark_models.py --with-batch1

cargo build --release
export ORT_DYLIB_PATH=/path/to/libonnxruntime.dylib

# the rate sweep
TPS="50 100 200 300 400 500" DURATION=15 scripts/run_benchmark.sh

# pinned against dynamic; ROWS must be 1, which the runner checks against the config
TPS="50 500" ROWS=1 MODELS="vectorized vectorized-batch1 named named-batch1" \
  scripts/run_benchmark.sh
```
