# CPU benchmark — vectorized vs named features

**Date** 2026-09-03 · **Host** MacBook Pro, Apple M1 Pro (8 performance + 2 efficiency cores),
32 GB · **Engine** ONNX Runtime 1.29.0, `cpu` provider, `intra_op_threads: 1`

One question: **does it cost more to reach a model through 22 transformed-and-concatenated
features than through 12 named inputs?** Everything else is held equal — same encoder, same
host, same engine, same rates.

Answer: **no, not below saturation.** Both paths sit within 1 ms of each other up to 400 req/s,
and feature handling is ~0.1% of a request either way.

---

## What was measured

Two transformer encoders, both classifying into 5 classes, both ~50M parameters. Counted from
the `.onnx` initializers rather than taken on trust:

| | `bench_model.onnx` | `bench_named_model.onnx` |
|---|---|---|
| **parameters** | **49,323,013** (49.32 M) | **50,070,533** (50.07 M) |
| nodes | 728 | 742 |
| opset | `ai.onnx` 17 | `ai.onnx` 17 + `ai.onnx.ml` 2 |
| inputs | 1 × `features FP32[rows, 502]` | 12, of which 2 are `STRING` |
| output | `scores FP32[rows, 5]` | `scores FP32[rows, 5]` |
| feature path | service transforms 22 features and concatenates them | one input per feature; text passed through verbatim |
| text handling | — | `LabelEncoder` + `Gather` **inside the graph** (2 each) |

The 1.5% parameter difference is the named model's in-graph embedding tables — the lookup that
lives in configuration for the vectorized model ships with the weights here.

**Load shape.** 1 row per request, 64 requests in flight maximum, `connection_concurrency: 100`,
20 s measured per rate after warmup. Offered load is open-loop: a request that finds no free slot
is **shed and counted**, never allowed to slow the generator down. So `achieved` below the
ceiling means the server genuinely kept up.

## Findings

**1. The two feature paths cost the same below saturation.** Requirement met. Comparing the two
models *within* a run at each rate up to 300 req/s gives eight pairings; seven of them differ by
under 0.35 ms on p50, and the largest is 1.15 ms (run 1 at 300 req/s: 12.93 vectorized against
11.78 named). For scale, the same model measured twice at the same rate varies by a comparable
amount — vectorized at 300 req/s read 12.93 and 11.89 across the two runs, a 1.04 ms spread with
nothing changed. Neither building one 502-wide vector nor building twelve smaller typed inputs is
where the time goes.

**2. Run 1's `vectorized @ 400` is an artifact, and the replicate is what shows it.** Taken alone,
run 1 reads as "named holds 400 req/s cleanly, vectorized starts shedding" — a real-looking
difference. But run 2 has vectorized clean at 400 (15.29 ms, 0 shed), statistically identical to
named's 14.59 ms. Every other 400 req/s measurement across both runs is 14.5–15.3 ms with zero
shedding; the 31.61 ms / 88 shed is one busy patch on the host. **This is the reason the benchmark
was run twice in opposite orders**, and it is worth keeping that habit: a single sequential sweep
would have shipped a wrong conclusion.

**3. At 600 req/s the two models are indistinguishable, and the run is what varies.** Within run 1
both shed ~3,170; within run 2 both shed ~1,350. The spread *between runs* is 2.3×; the spread
*between models* inside a run is under 2%. Past the ceiling the measurement reflects the host, not
the feature path.

**4. At 500 req/s named does degrade more gracefully, and that part is reproducible.** Vectorized
shed 453 and 480 across the two runs; named shed 87 and 74 — a consistent ~5× gap that survives
reordering. This is the one real difference found. It is a saturation-behaviour difference rather
than a per-request cost: both models achieve ~477–496 req/s, and the p50s at this rate (17–39 ms
named, 66–104 ms vectorized) are dominated by queue depth. The likely cause is the vectorized
path's single 502-float input arriving as one large allocation per request against twelve small
ones, which matters only once memory pressure and scheduling are the constraint.

**5. Feature handling is ~0.1% of a request**, from the server's own metrics — 46,000–48,000
batches per model per run:

| | vectorized | named |
|---|---|---|
| `VectorizationTime` mean | 13–18 µs | 10–12 µs |
| `VectorizationTime` median | 12–14 µs | 10–11 µs |
| `ToTensorTime` | **0 µs** (max 0) | **0 µs** (max 0) |
| `InferenceTime`, unsaturated | 10.02–10.16 ms | 10.33–10.49 ms |
| `InferenceTime`, saturated | 14.70–18.74 ms | 14.03–16.87 ms |
| **service share of a request** | **0.095–0.106%** | **0.086–0.110%** |

Two things fall out of this. `ToTensorTime` is 0 µs because the backend *wraps* the buffers rather
than copying them — the row-major columns are already the layout the engine wants. And
transforming 22 features into one wide vector is marginally **more** expensive than building 12
named inputs (13–18 µs against 10–12 µs), which is the opposite of the intuition that one big
input must be cheaper. Both are noise against 10 ms in the engine.

The practical consequence: **optimising the feature path cannot move this number.** Eliminating
vectorization entirely would return ~0.1% of a request. A faster model, fewer cores per request,
or an accelerator are the only levers.

**6. The ceiling is ~540 req/s achieved.** Eight performance cores at ~10 ms each is ~800 req/s in
theory. The shortfall is the two efficiency cores being much slower than the eight, plus the
background load described below. `InferenceTime` rising from ~10 ms unsaturated to ~15–19 ms
saturated is cores being shared, not the model changing.

## Caveats

- **The host was not quiet.** Load average was 6.5–13.5 before the runs, with Chrome, Zoom,
  WindowServer and a security agent (`uk.ava.reveal.agent.eps`) resident. Absolute latencies are
  therefore **pessimistic** against a dedicated machine, and the ~540 req/s ceiling is a floor on
  what this silicon can do. The A/B/B/A ordering controls for this in the *comparison*, which is
  what the benchmark is for, but the absolute numbers should not be quoted as the hardware's limit.
- **One row per request.** Batching amortises the engine's fixed costs and would change both the
  ceiling and the ratio between feature handling and inference.
- **`intra_op_threads: 1`.** One inference occupies one core, which is what makes the throughput
  arithmetic legible. A larger intra-op pool trades concurrency for single-request latency.
- **20 s per rate.** Enough for a stable p50 and p90; p99 at a single rate is one or two requests
  and moves around (`named @ 400` measured p99 16.41 and 128.12 in the two runs on identical p50s).
  Read p99 as an order of magnitude.
- CoreML was not measured here. It is a configuration value away, on a build with the `coreml`
  feature enabled.

## Reproducing this

```bash
conda activate local
pip install -r scripts/requirements.txt
python scripts/generate_benchmark_models.py       # writes models and configs together

cargo build --release
export ORT_DYLIB_PATH=/path/to/libonnxruntime.dylib

# run 1
TPS="50 100 200 300 400 500 600" DURATION=20 WARMUP=10 \
  RUN_DIR=/tmp/hushar-bench-cpu scripts/run_benchmark.sh

# run 2 — same rates, models reversed. This is the control, not a repeat.
MODELS="named vectorized" TPS="50 100 200 300 400 500 600" DURATION=20 WARMUP=10 \
  RUN_DIR=/tmp/hushar-bench-cpu-rev scripts/run_benchmark.sh
```

Server-side timings are the `metrics:` lines in `$RUN_DIR/logs/<tag>.server.log`, emitted once per
500 batches. Both runs also wrote inference logs to local disk (185 and 191 objects, ~52 MB each),
so the logging path was exercised under load throughout and shed nothing.
